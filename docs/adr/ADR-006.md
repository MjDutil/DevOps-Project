# ADR-006 — Pipeline único e observabilidade do fallback da IA

**Estado:** implementado e exercitado no mini-lab D6; revisão técnica preliminar aprovada e fechamento local autorizado; consolidado em `42128fa`, com publicação da entrega autorizada exclusivamente na branch B1. Resultados efetivos nas [evidências](../evidencias/desafio-6/README.md).

## Contexto e rastreabilidade

RF03/RF04 possuem integração HTTP opcional com FastAPI. O fallback mantém HTTP 200, portanto somente observar erros HTTP não revela a degradação. RF02 e RF05/RF06 precisam manter seus contratos durante a evolução operacional. Ranking, IA real e notificações duráveis continuam fora do mini-lab.

RNFs analisados: observabilidade, testabilidade, confiabilidade, deploy independente, recuperabilidade e desempenho. Até três ASRs prioritários:

| ASR | Cenário e resposta verificável |
|---|---|
| Testabilidade | Ao alterar o snapshot, Jenkins executa Maven e Python antes de arquivar um artefato aprovado; um teste falhando bloqueia essa aprovação. |
| Observabilidade | Ao interromper FastAPI, o contador `ia_fallback_total{operacao="recomendacao"/"assistente"}` aumenta, embora a resposta continue HTTP 200; Prometheus coleta e Grafana apresenta as séries. |
| Confiabilidade | A implantação local utiliza os mesmos bytes do JAR aprovado, conferidos por SHA-256; a recuperação da IA não exige reiniciar o Core. |

RPCs: Jenkins como base da esteira, Prometheus/Grafana obrigatórios, Java 17 no Core, preservar D1–D5 e contratos, sem socket Docker do host no Jenkins e sem infraestrutura de produção desnecessária. Java do controller e do build são versões separadas. Versões efetivamente resolvidas e plugins são registrados no laboratório.

## Alternativas e trade-offs

| Alternativa | Benefícios | Custos e limites |
|---|---|---|
| Pipeline único, com etapas por componente | Visão simples, mesma decisão de aprovação, menos configuração para uma equipe acadêmica | Maven e Python compartilham a fila; alteração de um componente executa ambos; falha Maven interrompe Python |
| Pipelines independentes Core/IA/gateway | Ciclos e execução separados; favorece deploy independente futuro | Mais jobs, coordenação de versões/contratos e evidências de integração; não necessário neste escopo |
| Apenas comandos locais | Menor custo operacional | Não demonstra o requisito Jenkins nem aprovação centralizada |

Escolhido pipeline único. Para métricas, comparar logs manuais (baixo custo, difícil correlação temporal) e contador Micrometer + Prometheus/Grafana (consulta temporal e painel, custo de coleta/storage). Escolhida a segunda: a degradação funcional não aparece necessariamente no status HTTP.

## Decisão

O Jenkins executa testes Maven/JaCoCo e testes Python com relatório JUnit. Somente após sucesso copia o JAR para `aprovado/`, registra hash, commit-base e hash do snapshot e arquiva tudo. Uma falha controlada gera JUnit somente no workspace descartável; o teste não entra no repositório. Relatórios da falha são arquivados, sem aprovar JAR.

O snapshot inclui fontes e configurações, com hashes por arquivo. O commit-base identifica o histórico anterior; **não identifica sozinho as alterações D6, que ainda não estavam commitadas durante a CI**. O manifesto identifica o conteúdo efetivamente construído. A documentação e as evidências posteriores não mudam os bytes aprovados; alterações posteriores em código exigem nova CI.

O controller utiliza Java 21; o build usa JDK 17/Maven. Plugins são resolvidos contra o Jenkins da imagem fixada e registrados. O executor do controller é usado apenas para este job local confiável; não é isolamento adequado para código não confiável em produção.

A implantação é uma ação local controlada pelo operador: baixa o JAR arquivado via API autenticada, confere SHA-256 e constrói imagem de runtime sem recompilar. Jenkins não acessa Docker nem implanta automaticamente. **É CI real e implantação local; não CD de produção.**

O Core registra contadores por duas operações fixas, sem IDs/perguntas nas etiquetas. Actuator HTTP/JMX é bloqueado na configuração padrão; somente o perfil `observabilidade-lab` expõe `health` e `prometheus` em porta interna separada. Prometheus coleta a cada dois segundos; Grafana possui datasource e dashboard provisionados. `up` mede sucesso de scrape, não disponibilidade funcional/SLA. HTTP 200 pode conter fallback; o contador de negócio complementa HTTP.

## Consequências e limites

- Contadores reiniciam com o processo. Prometheus preserva amostras no volume do laboratório; `increase` trata resets, sem tornar a métrica um histórico de negócio durável.
- Perfil de observabilidade usa H2 em memória e não valida PostgreSQL, HA, carga ou recuperação de dados. Não há alertas, TLS, RBAC de produção, promoção entre ambientes ou rollback automático.
- Portas administrativas ficam em loopback; credenciais aleatórias são arquivos ignorados. O endpoint interno de métricas não tem autenticação própria: o isolamento é a rede do laboratório.
- D4 continua melhor esforço em memória; D5 continua MQTT/QoS 1 com seus limites. Nenhum deles ganha persistência ou novas garantias por estar monitorado. Não foram adicionadas métricas específicas de D4/D5.
- FastAPI permanece demonstrativo. Seus testes de contrato/recuperação são integração; a etapa Python testa o gateway e compila sintaticamente os módulos Python.
- Download inicial de imagens/plugins/dependências exige rede. Digests e versões registradas limitam variação; repositórios externos podem ficar indisponíveis.
