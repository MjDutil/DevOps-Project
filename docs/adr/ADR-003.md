# ADR-003 — Fronteira opcional de IA com serviço Python

**Status:** adotada e validada no mini-lab D3 em 2026-11-03. [Evidências e limites](../evidencias/desafio-3/README.md).

## Contexto e requisitos

RF03 prevê recomendação inteligente; RF04 prevê assistente educacional com RAG/LLM. Modelos Python terão ciclo de atualização próprio e carga variável. O laboratório comprova a fronteira de integração usando respostas demonstrativas; não implementa modelos, busca vetorial ou LLM.

RNFs analisados: deploy independente (Supportability), escalabilidade e desempenho (Performance), tolerância a falhas (Reliability), interoperabilidade e manutenibilidade (Supportability/compatibilidade de integração). Interoperabilidade exige contrato HTTP/JSON; desempenho exige limitar a espera; manutenção favorece separar código Java e Python. Estes três últimos apoiam a decisão, sem ampliar a seleção de ASRs abaixo.

## Até três ASRs prioritários

| ASR | Como dirige a arquitetura |
|---|---|
| Tolerância a falhas | A indisponibilidade do Python exige timeout e resposta degradada no cliente; operações essenciais não dependem dessa chamada. |
| Deploy independente | O ciclo dos modelos exige um processo/artefato Python separado, que possa reiniciar sem reiniciar o Core. |
| Escalabilidade da IA | Carga variável justifica uma fronteira que permita dimensionar Python separadamente; réplicas e ganhos de capacidade ainda não foram demonstrados. |

## RPCs

Core permanece Java/Spring Boot; ML/RAG usam Python; indisponibilidade da IA não pode impedir operações essenciais. Reaproveitar Core, banco e regras AC1/D1/D2. A linguagem Python é uma restrição de implementação: sozinha não prova necessidade de serviço; autonomia de atualização e isolamento de falhas justificam a fronteira.

## Alternativas e trade-offs

| Alternativa | Benefícios | Custos / avaliação |
|---|---|---|
| A — IA embutida no Core | Chamadas locais e um deploy. | Implementação Java dos modelos viola a RPC Python; embutir runtime Python adiciona integração e compartilha ciclo de vida/falhas. Não escolhida. |
| B — Módulo Python acoplado ao ciclo do Core | Mantém Python e reduz a quantidade de unidades de entrega. | Processo filho ou pacote lançado junto ao Core exige ponte e compartilha atualização/recuperação. Menor autonomia, sem vantagem necessária neste laboratório. |
| C — Serviço Python independente via REST | Preserva RPC, permite reinício/entrega próprios e delimita falhas. | Adiciona latência, rede, contrato e operação de dois processos. Escolhida porque atende os três ASRs com a implementação já existente. |

ML e RAG ficam inicialmente na mesma API Python: dois endpoints, um serviço e menor custo operacional. Separar serviços quando houver evidência de cargas, dependências, recursos ou ciclos de atualização incompatíveis. Não há medição que justifique dois serviços hoje.

## Decisão e comportamento observado

Preservar `IaClient` e `IaController`, consumindo FastAPI por HTTP/JSON. A URL é configurada por `IA_BASE_URL`; no Compose é `http://ia:8000`. O Core não depende da inicialização de IA no Compose. Criação de aluno, conclusão de curso, fórum e Premium não chamam o serviço Python.

O cliente mantém timeout de conexão de **700 ms** e leitura de **1.200 ms**. São limites por fase, não um prazo total garantido; DNS, resolução e recursos sob carga exigem avaliação própria. `RestClientException` ou corpo nulo levam ao fallback. Não foi necessário alterar código de produção.

| Endpoint Core | Python | Degradação preservada |
|---|---|---|
| `GET /ia/recomendacoes/{id}` | `GET /recomendacoes/{aluno_id}` | HTTP 200, `status: indisponivel`, lista vazia e ID. |
| `GET /ia/assistente?pergunta=...` | `GET /assistente?pergunta=...` | HTTP 200, `status: indisponivel` e mensagem de indisponibilidade. |

A chamada IA é síncrona e ocupa uma thread enquanto espera. O fluxo essencial funciona em chamadas independentes; isso não prova proteção contra esgotamento de threads sob carga. Não se adicionaram retry, circuit breaker, broker ou novas dependências de produção: o mini-lab não demonstrou necessidade desses mecanismos.

## Evidência e consequências

O laboratório executou o JAR Spring e Uvicorn/FastAPI em portas locais reais, com H2: sucesso dos dois endpoints, interrupção do Python, fallback, operações essenciais e recuperação dos dois endpoints sem reinício do Core. Um servidor HTTP de teste com atraso de 3 s provocou fallback em **1.206,55 ms** e **1.206,38 ms**; durante essas esperas, conclusões passaram em **7,10 ms** e **6,85 ms**. São observações pontuais, não benchmark ou SLA.

A suíte Maven preservada aprovou 75 testes; o roteiro real contém 18 verificações HTTP aprovadas, separadas do Surefire. Timeouts de conexão são simulados na suíte existente; o limite real de 700 ms não foi medido. Conexão recusada no laboratório não equivale a timeout de conexão.

Riscos/limites: o cliente repassa mapas sem validar schema, HTTP 200 degradado exige inspeção do campo `status`, não há métricas específicas de fallback, e o protótipo não consulta dados reais do aluno nem implementa inteligência. PostgreSQL/Docker, navegador, carga, réplicas e deploy em infraestrutura externa não foram executados. A separação permite autonomia; o ensaio comprova reinício independente, não uma esteira de deploy.
