# ADR-003 — Fronteira opcional de IA com serviço Python

**Status:** Proposta incremental (laboratório B1, validar contra evidências)

**Contexto:** recomendação e assistente devem evoluir independentemente; falha da IA não pode travar fluxo essencial.

**RF:** RF03 recomendação e RF04 assistente. **RNFs (FURPS+):** disponibilidade/confiabilidade (Reliability), escalabilidade (Performance), deploy independente (Supportability).

**ASRs:** (1) tolerância a falhas obriga timeout e fallback no cliente; (2) deploy independente permite atualizar modelos sem redeploy do Core; (3) carga variável pode demandar réplicas do serviço Python.

**RPC:** Core Java, ML/RAG Python, IA opcional.

**Alternativas:** A — embutir IA no Java: poucos serviços, rompe RPC de linguagem; B — processo acoplado: falha e ciclo operacional ainda misturados; C — FastAPI independente: isolamento e escala próprios, aumenta custo HTTP/operação. Dentro de C, começar com uma API Python comum para ML/RAG; separar serviços apenas quando perfis de carga justificarem.

**Decisão:** C, FastAPI com contrato REST/JSON; timeouts, fallback para recomendações vazias/resposta indisponível, sem bloquear fluxos críticos.

**Consequências:** novos pontos de falha, monitoramento e versionamento de contratos; nenhuma IA real foi implementada neste laboratório.

**C4:** Container com Core → FastAPI.

**Evidência parcial (código, sem validação integrada):** `labs/ia` contém protótipo Python e `ia/IaClient` + `ia/IaController` contêm cliente Spring com timeout/fallback. **PENDENTE:** executar ambos, interromper FastAPI, capturar respostas/logs/tempos, validar os testes e guardar prints no Git.
